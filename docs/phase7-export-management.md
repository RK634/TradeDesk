# Phase 7 — Export Management

## Delivered functionality

- Organization-scoped export orders linked to active customers, products, and an inventory location.
- Order lines retain product/SKU/name snapshots and use `Decimal`/PostgreSQL `NUMERIC` values for quantities and prices.
- Draft → submitted → approved/rejected status flow with actor/time history.
- Approval checks available inventory and reserves every order line transactionally.
- Shipment creation dispatches only stock reserved for the selected order. Posting releases the relevant reservation and reduces on-hand stock atomically.
- Dispatch and delivery request idempotency keys prevent duplicate processing on client retries; reusing a key with a different payload returns HTTP 409.
- Partial shipment dispatches and partial delivery events are supported. Delivered quantities cannot exceed dispatched quantities or the original order quantities.
- Organization-scoped API endpoints and role permission checks cover reads, creation, submission, approval, dispatch, delivery, and cancellation.
- The application shell includes a working Export management page and the dashboard exposes persisted export-order counts.

## Key API endpoints

All endpoints are under `/api/v1` and require a signed-in session. Mutations also require same-origin and CSRF checks.

| Method | Endpoint | Purpose |
|---|---|---|
| GET / POST | `/exports` | List/search export orders or create a draft order |
| GET / PATCH | `/exports/{order_id}` | Read order details or update draft/rejected planning fields |
| POST | `/exports/{order_id}/submit` | Submit an order for approval |
| POST | `/exports/{order_id}/approve` | Validate stock and reserve inventory |
| POST | `/exports/{order_id}/reject` | Return a submitted order with a reason |
| POST | `/exports/{order_id}/cancel` | Cancel an eligible order and release unshipped reservations |
| GET / POST | `/exports/{order_id}/shipments` | List shipments or dispatch a shipment with line quantities |
| POST | `/exports/{order_id}/shipments/{shipment_id}/deliveries` | Record partial or full delivery quantities |
| GET | `/exports/{order_id}/deliveries` | List delivery events |
| GET | `/dashboard/summary` | Includes organization-scoped export metrics |

## Inventory integrity

On approval, inventory is reserved from the order's selected source location. Dispatch is allowed only against a reservation and only up to the unshipped reserved quantity. The dispatch transaction writes a reservation-release movement and a goods-dispatched movement, then updates the export order line and shipment records. These writes are committed together, so a failure rolls back all effects. Each shipment and delivery stores a request hash with its idempotency key; exact retries return the original record, while a changed request with the same key is rejected.

On cancellation, outstanding reservations are released, but orders with dispatch history cannot be cancelled through this endpoint. Delivery records are kept as historical events; dispatch already reduces inventory, so delivery does not deduct it a second time.

## Known limitations

- The frontend creation form currently creates one initial product line. The API supports multiple lines, but richer order-line editing is a follow-up enhancement.
- Shipment references and delivery references are manually supplied or generated by the frontend; external carrier tracking is not integrated.
- Generalized export document workflows, quotations as separate records, invoices, payments, and currency conversion are reserved for later phases.
- The full frontend production build and real PostgreSQL/Docker runtime checks must be run in a development environment with installed dependencies and services.
